## 1. Summary

Wrenyard attaches its Desktop application to the daemon of another device over
SSH, in the spirit of VS Code Remote. While connected, the whole application
works in remote mode: every business surface reads and writes the remote
daemon's data, not the local machine's.

This document records the requirement set from the Notes source, the verified
architecture, the implemented design for the SSH relay and the single-active
context, the recorded target-platform decision, and the verification and
acceptance state. The first version provisions remote daemons only onto the
platforms Wrenyard already ships (§7); broader platforms are explicit future
work.

## 2. Requirements carried verbatim from Notes `9ed63dc8`

These are the note-derived requirements. They are the authority.

1. **SSH connection to another device's daemon**, comparable to VS Code Remote:
   the client connects over SSH to the daemon running on the other device.
2. **Discover local SSH hosts** from the machine's SSH configuration.
3. **First-connect daemon install**: connecting to a host that has no usable
   daemon installs it.
4. **Remember only successful connections.** Failed attempts are not remembered.
5. **Saved-host direct connection**: a host that was added successfully can be
   connected to directly.
6. **Whole-application remote mode.** While connected, the entire app operates
   remotely.
7. **Entry point**: `Daemon > 远程连接 > 新增` opens a modal that is normally
   hidden.
8. **One list, two sources.** Saved hosts and the default *Add* option appear in
   the same list.
9. **Discovered host display** shows display name, IP, and OS. Facts that are not
   yet known must be shown honestly as unknown until probed; do not fabricate.
10. **Form adds an SSH configuration** with independent **Test** and **Confirm**
    actions, debounced silent validation, and feedback to the user.
11. **Validation precedes connection and save.** A connection is established and
    saved only after validation succeeds.
12. **Connection metadata is owned by daemon config** (not by Desktop settings).
13. **Existing display names can be renamed.**

**Explicitly out of scope this cycle (per Notes):**

- No simultaneous local + remote operation.
- No multiple windows / multiple contexts.
- No arbitrary extra features beyond the above.

## 3. Baseline architecture (at base `6112d9d7`)

Recorded during exploration of worktree `wy-remot` at base `6112d9d7`. This is
the starting point the implementation was built on, not the current state (see
§12 for the current implementation).

### 3.1 Control plane

- `@wrenyard/control` lives in `packages/control`.
- Transport is an **owner-only Unix domain socket / Windows named pipe**.
- Framing is **NDJSON JSON-RPC** with a **`protocolVersion=2` handshake** and a
  **30s ordinary timeout**.
- Events are delivered by **polling / long polling**.
- **base64 media** payloads are supported.

### 3.2 Desktop wiring

- `apps/desktop/src/main.ts` fixed `ipcPath` and threaded it into a **per-call
  `requestForeman`**, the shared **daemon client / subscriptions**, the
  **provider service**, the **health probe**, and the **session bridges**.
- **Local bypasses** (operations that did not go through the control client):
  workspace inspect/init, media pick/reveal, settings/logs opens, and the daemon
  supervisor.

### 3.3 Daemon configuration (baseline)

- Configuration lives in `apps/daemon/lib/config/data.mts`, with **atomic
  mode-`0600` writes** through the config manager/writer.
- `workspace.switch` existed as a daemon operation.
- **`workspace.inspect` did not exist** as a daemon operation. It is now
  implemented (§12), together with `workspace.initialize`.

### 3.4 Distribution (baseline)

- `tools/release/pack.mjs` staged `resources/wrenyard` runtime + node, plus
  `daemon/daemon.mjs`, with native `better-sqlite3` and `sharp`, and the DSH
  closure.
- Releases were **macOS ARM64 (DMG/ZIP)** and **Windows x64 (NSIS EXE)** only.
- A **standalone daemon package did not exist**. The remote bootstrap payload
  builder (§12) now produces one from the same staged closure; there is still no
  Linux release target.
- Same-product-version and IPC handshake failures **fail closed**.

### 3.5 Constraints carried forward

- Do not use obsolete suite/install scripts.
- Do not expose an unauthenticated TCP listener or a public REST surface.

## 4. Design goals and invariants

- **G1 — One active endpoint.** Exactly one daemon endpoint is active at a time;
  local and remote are never both active.
- **G2 — No silent fallback.** Losing the tunnel produces an explicit
  disconnected-remote state; it never silently becomes local.
- **G3 — No local side effects for remote data.** Remote workspace paths are
  never stat'ed, created, or revealed locally.
- **G4 — Daemon owns connection metadata.** No Desktop-side settings store
  becomes a second source of truth for hosts.
- **G5 — No secrets in app storage.** No passwords or private keys are stored,
  logged, or placed in argv.
- **G6 — Nothing is remembered unless it succeeded.** Failed probes, failed
  installs, and failed confirmations leave no remembered host and no context
  switch.

## 5. Design (implemented)

> This section is the implemented design. Where the baseline design language
> ("must", "proposed") is retained, it describes behaviour that now exists in
> the tree; §12 maps it to modules.

### 5.1 SSH client and host discovery

- The **native OpenSSH client** is used rather than a bundled SSH library.
- Invoked with `BatchMode=yes`, `StrictHostKeyChecking=yes` and
  `ForwardAgent=no`, with bounded connect/probe timeouts.
- **Existing agent/key authentication and SSH config routing** are supported
  (the user's `Host` blocks, `ProxyJump`, etc.).
- **No passwords and no private keys** are stored, logged, or placed in argv.
- **No automatic host-key acceptance.** An unknown or changed host key fails
  with an actionable message telling the user to enroll the host manually with
  `ssh` outside the application. Verification never touches personal
  `~/.ssh/config` or `~/.ssh/known_hosts`.
- **Concrete `Host` aliases** are enumerated, including `Include` support, and
  `ssh -G <alias>` provides the **effective** configuration.
- **Wildcard and negated patterns** (`*`, `?`, `!...`) are never listed as hosts.
- SSH configuration is treated as **user-trusted input**. `ssh -G` is not
  claimed to be side-effect free where `Match exec` is present.

### 5.2 Host form: validation

- Validation is **ephemeral** and runs over **safe structured fields** plus the
  alias.
- **Newline and option injection are rejected**; unchecked values are never
  concatenated into a shell command.
- Validation is **debounced and silent** during typing.
- **Test** and **Confirm** are independent actions.
- An independently updated form **invalidates prior validation**; stale async
  probe results are **ignored**.

### 5.3 Confirm: append a Host stanza as a transaction

`Confirm` is a transaction:

1. Validate the **current candidate** (not a stale one).
2. Run the **authoritative idle check** against the endpoint being left, then
   verify **daemon compatibility and readiness** on the target.
3. Only then **append a nonconflicting `Host` stanza**, preserving existing
   config content and restrictive file permissions.
4. On save/append failure: **no remembered host and no context switch**; the
   appended stanza is rewound to its exact previous bytes (a rollback conflict
   is surfaced, not swallowed).

Silent probes and **Test** read platform/arch and authentication **without
installing**. Actual install happens **only on Confirm**.

OS is detected **remotely**. A `HostName` resolved from SSH config is **not**
labelled as a resolved numeric IP.

### 5.4 Transport: SSH-owned stdio relay

- Daemon IPC is relayed over **SSH-owned stdio** to the target daemon's
  owner-only IPC through the daemon bundle's `--stdio-bridge --connect-to
  <ipcPath>` entry, which emits one clean NDJSON stdout and refuses any network
  endpoint.
- The relay is bridged behind a **local owner-only endpoint** (Unix socket, or
  named pipe on Windows) so that **all existing control clients share one active
  endpoint**.
- **No open network daemon listener.**
- **No app-driven agent or credential forwarding.**
- **Frames, handshake, timeouts, and cancellation** are preserved; buffering is
  **bounded in both directions** and over-limit backlogs drop the connection.
- **Only owned relay/daemon processes** are cleaned up — never processes
  Wrenyard did not start.

Remote bootstrap command quoting is **platform-specific**:

- POSIX: each argument is **single-quoted** (embedded single quotes escaped);
  NUL/CR/LF are refused.
- Windows OpenSSH (`cmd.exe`): each argument is **double-quoted**, and any value
  containing `"`, `%`, `!`, NUL, CR or LF **fails closed** (there is no reliable
  escape for a quote inside a double-quoted cmd.exe argument, so no
  backslash-escaped quote is ever emitted).
- Dynamic Node sources travel **base64-encoded** through a fixed loader so no
  quote/backslash/`!` in the source reaches cmd quoting; PowerShell steps run via
  **`-EncodedCommand` (UTF-16LE)** so no script text reaches the shell's quoting.

### 5.5 Bootstrap and install

- **Versioned per-user bootstrap**, no sudo / no system-wide install: everything
  lives under `<home>/.wrenyard/remote/<version>`.
- **First-version install targets are `darwin-arm64` and `win32-x64` only**
  (§7). Any other verified target OS/arch fails with an explicit
  **unsupported OS/arch** outcome and is not remembered.
- **Checksum-verified, target-compatible payload** downloaded from the shared
  update feed's `remote_payloads` entry (the same `WRENYARD_UPDATE_BASE_URL`
  convention the Desktop updater already uses). The digest is re-verified **on
  the target**; a digest-less direct URL is a loopback-fixture-only affordance.
- **Atomic readiness marker**: extraction goes into a unique owned sibling
  staging directory, then a `READY` marker (version + target + sha256) is written
  inside staging and the whole directory is renamed into the final prefix. A
  prefix that already carries a `READY` marker is **refused rather than
  overwritten**, so a live payload is never deleted blindly.
- **Target-native verification before publishing**: the staged payload's
  `SUITE_VERSION` must name the exact version, every required entry must exist,
  and the **staged runtime's actual `process.platform`/`process.arch` must equal
  the selected target** before the ready payload is published (a macOS x64 Node
  can run under Rosetta, so a successful exec alone is not proof). Reuse of an
  existing prefix applies the same version/target/entry/platform/arch checks.
- **Do not replace an incompatible running daemon.** A reachable daemon is probed
  for the exact product and protocol version: a compatible one is adopted, a
  reachable-but-malformed/erroring/version-mismatched endpoint **fails closed**.
- A failed install is **not remembered**, and **retry is allowed**.
- Errors are **distinguished**: authentication, host-key, unsupported OS/arch,
  transfer/checksum, launch, incompatible version, timeout, and persistence.
- Pre-extraction staging uses **native tooling only** (POSIX shell / PowerShell:
  `mkdir`/`sh`, `tar`, `shasum`/`Get-FileHash`) because the bundled Node is not on
  the target until the archive is unpacked — the "needs Node before Node is
  uploaded" paradox is repaired, not assumed away.
- A cross-platform payload copy is never claimed to work with native modules.

### 5.6 Single active context

- A **central active-connection generation** with states:
  `local` / `connecting` / `remote` / `disconnected`.
- **Business access is gated**: allowed only for a committed endpoint (`local` or
  `remote`); `connecting` and `disconnected` are denied.
- **New actions are fenced during switches**; the transition lock and generation
  are taken **before the first await**.
- **Active app operations are waited for or rejected** rather than killed: a
  switch is refused while user work or daemon-side activity is in flight.
- On switch, **old clients and long polls are invalidated/closed together with**
  session selection/drafts and provider/quota/statistics/pet/scheduler/task/
  project/workspace caches.
- **Late results from a prior generation are rejected.**
- **All business data and actions use the active endpoint.**
- **After host-registry persistence the commit is non-throwing and explicit**:
  the endpoint retarget is a deterministic assignment that is never rolled back
  inside the context. If the follow-up cache refresh fails, the result is an
  **explicit committed remote with the host retained and a surfaced refresh
  error** — never a false unsaved/failed state and never a silent registry
  rollback.
- On tunnel loss, the state stays explicitly **`disconnected` (remote)**; it
  **never silently falls back to local**.
- An explicit **return-to-local refreshes all views** and **does not stop an
  externally owned remote daemon**.
- The **local daemon retains only host-registry management** (no simultaneous
  local work).

### 5.7 Persistence

- **Host alias, display name, and verified platform metadata** are persisted via
  daemon IPC into the **originating daemon config** — no Desktop settings SSOT
  and no secrets — and **only after compatible remote readiness**. The registry
  record is **secret-free** and the config write is atomic at mode `0600`.
- `remote.host.list` / `remote.host.save` / `remote.host.rename` are daemon
  operations; `remote.host.save` requires `ready: true` and rejects an unready or
  missing-`ready` payload without changing the registry.
- **`workspace.inspect` and `workspace.initialize` are daemon operations**, so
  remote workspace paths are never stat'ed or created locally.

### 5.8 Surface behaviour under remote mode

- **Local pick/clipboard is allowed only as an explicit upload**, transferring
  bytes as attachments.
- **Remote media paths are fetched via `session.media.read`** and never revealed
  locally.
- **Remote workspace/settings/logs actions operate remotely or are explicitly
  unavailable** — never open same-named local paths.
- **Visual preferences and client update remain local client concerns** and are
  labelled as such.
- Remote mode does **not** route daemon restart/shutdown or updater callbacks to
  the **local supervisor**.

## 7. First-release SSH target OS/architectures (decision recorded)

**Decision (recorded):** the first version of remote daemon installation
supports **macOS ARM64 (`darwin-arm64`)** and **Windows x64 (`win32-x64`)** only
— the platforms Wrenyard already ships and maintains. No other platform is a
first-version install target.

Rationale: today's releases ship only macOS ARM64 and Windows x64 Desktop
packages, and there is no maintained Linux release. Limiting the first version to
the existing target matrix keeps the bootstrap payload within the packaging
closure that already exists, with no release-matrix expansion.

Consequences for the first version:

- The payload is built from the **existing packaging closure** (bundled Node, the
  daemon bundle, and its native dependency closure), not from source on the
  target. The **Windows NSIS Desktop installer is not a daemon archive** and is
  not reused as a payload.
- The payload builder supports an explicit **cross-platform source-and-target**
  build (for example staging on macOS for a Windows target), and it asserts that
  a non-native stage is genuinely target-native rather than silently shipping the
  wrong native closure.
- A first connect to a host whose verified platform is **outside this matrix**
  fails with an explicit **unsupported OS/arch** outcome and is **not
  remembered**; it never silently copies a mismatched payload.

### 7.1 Future work (not in the first version)

These are explicitly deferred; they are **not** first-version requirements and
must not be implemented by expanding the release matrix:

- **Linux x64** and **Linux ARM64** remote daemons.
- **macOS x64** remote daemons.

Adding any of these later requires native dependency packaging and
release-verification coverage outside the current maintained matrix, and is
tracked as future work rather than as part of this cycle.

### 7.2 Explicit anti-decisions

- **Do not silently choose "same-platform-only copy."**
- **Do not silently choose "connect to an existing daemon only."**
- Neither satisfies general first-connect provisioning within the recorded
  matrix.

## 11. Coordinator checklist

### 11.1 Commands available today

- Static checks: `pnpm lint`, `pnpm check`.
- Tests: `pnpm test` (existing suites only; the `session-media-packaging` and
  `docs/model-providers.md` issues in §9.1 are pre-existing).
- Build one remote payload for a target from an already-staged closure:
  `node tools/release/remote-payload.mjs --stage <staged-dir> --version <x.y.z>
  --target <darwin-arm64|win32-x64> [--source <triplet>] [--out <dir>]`.
- Full release packaging for the current target: `pnpm release <x.y.z>` (this
  runs `pack.mjs`, which also builds that target's remote payload).
- Generate the matching-version feed document (adds `remote_payloads`):
  `node tools/release/update-feed.mjs <metadata-dir> <assets-dir> --version
  <x.y.z> --repository <owner/repo>`.
- Point the Desktop at a controlled feed with `WRENYARD_UPDATE_BASE_URL`.

### 11.2 Required before first-install acceptance

1. Build both native payloads (`darwin-arm64` and `win32-x64`) for the candidate
   version, e.g. each on its own target runner so the staged native closure is
   genuine.
2. Publish a **matching-version feed** whose `remote_payloads` lists both
   archives with their sha256 digests.
3. Set `WRENYARD_UPDATE_BASE_URL` to that controlled source (or use a later
   approved release).
4. Do **not** modify immutable published version metadata.

### 11.3 Coordinator acceptance checklist

1. Both targets install, and a cross-source-and-target build is exercised.
2. Strict existing SSH trust (no auto host-key acceptance).
3. First install runs once on a clean target and remembers one host.
4. A saved host reconnects directly with no duplicate install.
5. A failed auth / key / checksum / version attempt saves nothing.
6. Rename persists across reload.
7. A sentinel remote host shows remote business context while the local sentinel
   stays untouched.
8. Attachments upload explicitly to the remote.
9. Disconnect shows explicit remote-disconnected with no local fallback.
10. Explicit return-local clears remote views.
11. An active session blocks a switch.
