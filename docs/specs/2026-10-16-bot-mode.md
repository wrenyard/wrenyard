# Bot mode: autonomous dispatcher

> Created: 2026-10-16
> Status: approved 2026-10-16; implementation in progress
> Refs: bot-mode

## 1. Goal and non-goals

Bot mode is a daemon-owned, long-running agent (the "chief dispatcher") that
replaces the hand-run coordinator loop:

1. poll a user inbox for work items,
2. confirm each request is real,
3. dispatch each item to its own session and managed worktree,
4. supervise progress and correct direction,
5. run real-machine acceptance with evidence,
6. deliver one item at a time: rebase, accept, merge, push,
7. complete the source item and notify the user with the result.

It is a generic product capability. Every integration that touches the user's
private tools (inbox, notifier, acceptance drivers, chat targets, database
paths, credentials, scripts) is user-local configuration outside this
repository. Source code, docs and tests use neutral examples only.

Non-goals: the bot does not restart, upgrade or install the daemon or Desktop
it runs in; it does not tag or release unless a project release policy
explicitly enables it; it never force-pushes.

## 2. Requirements from the hand-run loop

Each pitfall in the coordinator-loop lessons is a requirement:

| # | Requirement | Where |
| --- | --- | --- |
| R1 | Every item runs in its own managed worktree; alert when executions for a bot item run in the project checkout or pile up as `queued`. | §5.3, §9 |
| R2 | Bot state survives daemon restart/upgrade; every step resumes idempotently. | §3, §5.4 |
| R3 | Follow-ups always reuse the session's own model. | §6.2 |
| R4 | Full session ids only; a failed send is an error, never silent. | §6.2 |
| R5 | Only the bot merges/pushes, and only after acceptance; sessions commit in their worktree only. | §5.3, §11 |
| R6 | Rebase before acceptance; on conflict send the session the conflicting files and the main commits that caused them; sequence items touching the same files. | §5.3, §8 |
| R7 | Back off dispatch under load; keep a bot concurrency budget. | §7.3, §9 |
| R8 | The bot never restarts the daemon it runs in. | §1, §9 |
| R9 | Acceptance exercises the real UI/data path, records evidence, and states what was not verified. | §8 |
| R10 | Before completing a source item, re-read it by id and check it is still open and unchanged. | §5.3 |
| R11 | Native surfaces use desktop computer use; report when it could not. | §8 |
| R12 | Items needing a user decision are parked with a precise question; other items continue. | §5.2, §10 |
| R13 | Private integrations are user-local commands/MCP tools, never code. | §6 |

## 3. Identity and lifecycle

- A workspace may own any number of bots. A bot has a stable id (8 hex chars,
  like schedules), a display name, a workspace root, a config file reference,
  a `mode` (`live` | `dryRun`) and a `state`.
- States: `running`, `paused`, `stopped`.
  - `pause`: finish the step in flight, start no new step, keep polling off.
    Work sessions keep running; they are not interrupted.
  - `resume`: continue from persisted item states.
  - `stop`: like pause, plus the bot is excluded from automatic start after a
    daemon restart. Items keep their state and can be resumed.
  - `delete`: only from `stopped`; removes bot rows, never worktrees, sessions
    or branches (cleanup is a separate explicit action per item).
- No expiry. Unlike `schedule.*` (7-day recurring expiry), a bot runs until
  paused or stopped.
- The bot never upgrades, restarts or reinstalls the app or daemon it runs in;
  that is always a separate, user-supervised step.
- Durable state lives in the daemon SQLite database `wrenyard.db` (new tables,
  §5.4), created idempotently in `bootstrapSchema`. It survives daemon restart
  and suite upgrade. The bot host is a daemon service started after the IPC
  server listens, scoped to the active workspace exactly like the scheduler
  (records of other workspaces are neither listed nor ticked; a workspace hot
  switch flushes and swaps the host).
- On start the host reconciles every item with a `pending` step (§5.4) before
  taking new work.

## 4. Architecture

```text
Bot host (daemon service, deterministic)
  ├─ tick loop: poll inbox, advance items, watchdogs
  ├─ step executor: idempotent steps with a journal
  ├─ adapters: inbox / notifier (user-local command or MCP tool)
  ├─ judgment tasks (structured output, own model per policy)
  │    bot-verify  : is the request real, class, brief, acceptance plan
  │    bot-review  : continue | correct(text) | ready | park(question)
  │    test        : acceptance with browser-use / computer-use features
  └─ project/session methods: worktree create/rebase/merge, push, session.*
Work sessions (normal ledger sessions, one per item, tagged with bot metadata)
Desktop Bot page (bot.* methods, polling)
```

The host itself never reasons. All side effects are deterministic steps; all
judgment is delegated to task runs with structured output, timeouts and
artifacts, so every decision is inspectable and the host stays cheap.
Task-backed steps (verify, review, accept) are detached: a tick starts the task
run and records its run id; later ticks poll its status, so no tick waits for a
model run and items of different projects progress in parallel.

## 5. Item state machine

### 5.1 States

| State | Meaning | Leaves to |
| --- | --- | --- |
| `discovered` | Seen in `inbox.list`; snapshot stored. | `verifying` |
| `verifying` | `bot-verify` running on current main. | `verified`, `dismissed`, `parked`, `failed` |
| `verified` | Request confirmed; class, brief and acceptance plan stored. | `dispatched` |
| `dispatched` | Worktree created, session created, brief delivered. | `in_progress` |
| `in_progress` | Session working; reviewed on new activity. | `ready`, `parked`, `failed` |
| `ready` | Session idle, worktree clean with commits ahead, review says ready. | `accepting` (when the delivery lane is free) |
| `accepting` | Holds its project's delivery lane: rebase, then acceptance. | `accepted`, `rejected`, `parked` |
| `accepted` | All required checks verified. | `merging` |
| `rejected` | Acceptance or rebase failed; correction sent. | `in_progress`, `failed` |
| `merging` | Merge into the project default branch, then push. | `merged`, `failed`, `parked` |
| `merged` | Merged and pushed (or recorded as would-merge in dry run). | `completing` |
| `completing` | Re-read source item, complete it, notify. | `completed`, `parked` |
| `completed` | Source completed and user notified. Terminal. | — |
| `dismissed` | Request not real or already done; user notified with reason; source annotated/released per policy. Terminal. | — |
| `parked` | Waiting for a user decision; holds a precise question. | the state it came from, or `dismissed`/`withdrawn`/`failed` |
| `failed` | Retries or budgets exhausted; user notified; source annotated/released per policy. Terminal until manual retry. | `discovered` (manual retry) |
| `withdrawn` | The source item disappeared from `inbox.list` or was completed elsewhere while in flight (§5.5). Never merged; user notified. Terminal. | — |

`merged+pushed` and `completed+notified` from the request map to `merged` and
`completed`; their sub-steps are separate journal entries.

### 5.2 Parking

Any state may park. A parked item stores `question`, optional `options[]`,
`parkedFrom` and context. The question goes to the Bot page and, once, to the
notifier. The user answers on the Bot page only (`bot.item.action` with
`answer`). The inbox `annotate` op only writes back to the source; the bot
never reads answers from the inbox. The answer is appended to the item context
and the item returns to `parkedFrom`. A parked item never holds its project's
delivery lane: entering `parked` from `accepting` or `merging` releases it.

### 5.3 Steps per transition

Every side effect is a named step with an idempotency key
`<itemId>:<generation>:<step>:<attempt>`.

- verify: run `bot-verify` (read-only intent) in the project checkout on the
  current default branch. Output: `real` (bool) + `reason`, `class`
  (`default` | `simple` | `visual` | user-defined), `project`, brief
  (verbatim request + context + acceptance criteria), acceptance plan
  (required checks, surface per check: `daemon` | `renderer` | `native`),
  predicted touched paths, or `park` with a question.
- dispatch:
  1. `worktree.create`: deterministic id derived from bot id + item id (8
     chars, `[A-Za-z0-9_-]`); create only if `project.worktree.list` lacks it.
     The worktree metadata records `owner: bot:<botId>/<itemId>`.
  2. `session.create`; store the full session id; set session metadata
     `{ bot: <botId>, item: <itemId> }`.
  3. `session.send` the brief with the routed model. The brief names the
     worktree id so dispatched task runs bind it, and states the rules:
     minimal diff, no tests unless needed, commit locally with a
     `Refs: bot/<itemId>` trailer, never merge/push/tag/release, end with a
     line `BOT-READY <head sha>` when done or `BOT-BLOCKED <question>`.
- supervise (in_progress): on new ledger events or idle timeout, run
  `bot-review` with the request, brief, recent turns and `project.diff` of the
  worktree. Results: `continue`; `correct` → `session.send` correction text;
  `ready`; `park` with question. Corrections are capped by budget (§9).
- ready check: session not running, worktree clean, commits ahead of the
  default branch, last reply has `BOT-READY`, review returned `ready`.
- accept (lane holder only):
  1. `worktree.rebase` onto the default branch (new method, §12). On conflict:
     `rejected`, and the session receives the conflicting paths plus the
     default-branch commits since the merge base that touched them.
  2. acceptance per §8 against the rebased head.
- merge: `project.worktree.merge` (bot-only, §11), then `project.push` for the
  project. Merge and push are separate steps with separate keys.
- complete: `inbox.get(sourceId)`; require `open == true` and the same
  fingerprint (hash of title + notes) as dispatched, else park. Then
  `inbox.complete(sourceId)`.
- notify: one message per item: title, project, outcome, merged commit sha(s),
  pushed remote/branch, verified checks with evidence media, and an explicit
  "not verified" list.

The project lane is acquired by a deterministic `ready → accepting` transition
before any acceptance step runs; steps of lane states run only while the item
holds its lane. Lane rows are acquired and released inside the same store
transaction that writes the item state, so every path (step results, failures,
user actions, cleanup) keeps the lane consistent. A handler error in a lane
state parks the item with the error, releasing the lane.

### 5.4 Persistence, idempotency, at-most-once

New tables (created with `CREATE TABLE IF NOT EXISTS`):

- `bot(id, workspace_root, name, config_path, config_hash, state, mode,
  last_tick_at, next_poll_at, created_at, updated_at)`
- `bot_lane(workspace_root, project, bot_id, item_id, acquired_at)` with
  `PRIMARY KEY(workspace_root, project)`: one delivering item per project
  across all bots of the workspace.
- `bot_item(id, bot_id, source_id, generation, fingerprint, title, body,
  project, class, state, parked_from, question, answer, session_id,
  session_model, worktree_id, branch, head_sha, merged_sha, acceptance,
  counters, error, created_at, updated_at)` with
  `UNIQUE(bot_id, source_id, generation)`. A source item seen again after a
  terminal state starts a new generation only if it is open and its
  fingerprint changed.
- `bot_step(id, item_id, idem_key UNIQUE, kind, status, input, output, error,
  started_at, finished_at)` where status is `pending` | `done` | `failed` |
  `unknown`.
- `bot_log(seq, bot_id, item_id, at, level, code, message)` with a bounded
  per-bot retention.

Step protocol: insert `pending` in a transaction with the item state, perform
the effect, then write `done` + output and the next item state in one
transaction. A step is marked started (`started_at` written in its own
transaction) immediately before its effect runs. Restart reconciliation probes
only started `pending` steps; a pending step that never started is simply run.
The session binding `{ bot, item }` is stored on `bot_item` (session metadata
only carries archived/pinned), so the `session.create` probe cannot detect a
session created just before a crash; it creates a new one and the orphaned
empty session is harmless. Restart reconciliation for a `pending` step probes
instead of repeating:

| Step | Probe |
| --- | --- |
| worktree.create | worktree id present in `project.worktree.list` |
| session.create | session with metadata `item == <itemId>` exists |
| session.send | the session ledger has a user turn containing the step marker `[bot:<idem_key>]` |
| rebase | branch head already contains the default-branch head |
| merge | worktree head sha is an ancestor of the default branch |
| push | local default branch equals its upstream |
| inbox.complete | `inbox.get` reports not open |
| notify | none possible: mark `unknown`, never resend; show on the Bot page |

This gives at-most-once delivery for every outward effect: a step that cannot
be proven done and cannot be probed is never retried automatically.

### 5.5 Source withdrawal

The source can change while an item is in flight (`verified` through
`completing`). Checks run after every successful `inbox.list`, immediately
before `merge`, and immediately before `inbox.complete`. An item absent from a
successful list is confirmed with `inbox.get`; an adapter error is never
treated as withdrawal. If the source is gone or no longer open, the item moves
to `withdrawn`: no merge, push or completion; the project lane is released;
the user is notified; the session and worktree are left intact for inspection
and removed only by an explicit `cleanup`. If the source is still open but its
fingerprint changed, the item is parked with the reason `source changed` and
the old and new title; the answer is either `continue` (the bot sends the new
text to the session and returns the item to `in_progress`) or `dismiss`.

## 6. Adapters (user-local)

### 6.1 Configuration location and shape

Bot configuration lives in the user's config home, never in a workspace or
repository: `<configHome>/bots/<name>.json` (`<configHome>` resolves as
`WRENYARD_CONFIG_HOME` or the platform default). The daemon stores only the
path and a content hash; edits take effect on the next tick after validation.
Secrets are never written in the file: values may reference environment
variables (`"${env:NAME}"`) resolved at execution time from the daemon
environment.

An adapter is one of:

- `command`: `{ "kind": "command", "argv": [...], "cwd"?, "env"?,
  "timeoutMs" }`. Runs without a shell (argv only), receives one JSON request
  on stdin and must print one JSON object on stdout. Uses the shared executor
  with timeout, output caps and process-tree kill.
- `mcp`: `{ "kind": "mcp", "server": <McpServer descriptor, same format as
  WRENYARD_COMPUTER_USE_MCP>, "tool": "<name>", "timeoutMs" }`. The request
  object is passed as tool arguments; the tool's JSON text result is parsed.

Inbox operations (`op` field): `list` → `{ items: [{ id, title, body?,
project?, url?, updatedAt? }] }`; `get` `{ id }` → `{ item: {..., open} |
null }`; `complete` `{ id }` → `{ ok }`; optional `annotate` `{ id, text }`
and `release` `{ id }` (take the item out of the bot's filter, e.g. remove a
label). Notifier: `send` `{ text, media?: [{ path, kind }] }` →
`{ ok, messageId? }`.

Responses are validated against JSON schemas; invalid output is an adapter
error. Logs record op, adapter name, duration, exit code/status, item counts
and ids, never raw stdout/stderr, argv values from `env` references, or
request bodies. All log strings pass the daemon redaction utilities.

### 6.2 Sessions and models

- `session.send` requires an explicit model. The bot stores the model used for
  the dispatch send in `session_model`. Before every follow-up it reads the
  latest `turn.started` model from `session.events` and uses that; if it
  differs from `session_model` (the user switched), it adopts the session's
  model and logs it. The routing policy chooses a model only for the first
  turn.
- Only full session ids are stored and used. A send error marks the step
  `failed`, retries with back-off up to the budget, then escalates.

### 6.3 Neutral example

```json
{

  "inbox": {
    "kind": "command",
    "argv": ["/path/to/inbox-adapter", "--filter", "bot"],

  },
  "notifier": {
    "kind": "command",
    "argv": ["/path/to/notify-adapter"],
    "env": { "NOTIFY_TOKEN": "${env:NOTIFY_TOKEN}" },

  },
  "projects": [
    { "id": "example", "match": ["example"], "merge": true, "push": true,
      "release": { "enabled": false } }

    "simple":     { "provider": "<provider>", "model": "<model>", "reasoningEffort": "medium" },
    "visual":     { "provider": "<provider>", "model": "<model>", "reasoningEffort": "high" },
    "acceptance": { "provider": "<provider>", "model": "<computer-use-model>", "reasoningEffort": "high",
                    "target": "<provider>/<model>:<client>" },
    "judgment":   { "provider": "<provider>", "model": "<strong-general-model>", "reasoningEffort": "high",
```

## 7. Policies

### 7.1 Scope

Only projects listed in `projects` are in scope. An item maps to a project
through the adapter's `project` hint or `bot-verify`; an unmapped item is
parked with a question. The inbox filter (which items, labels, lists) is the
adapter's responsibility.

### 7.2 Model routing

`routing` maps item class to a model triple. `bot-verify` assigns the class.
`acceptance` is the model for acceptance task runs (pick one strong at
computer use); `judgment` is for `bot-verify` and `bot-review`. Routing
references only registered, available targets; an unavailable target parks
the item instead of guessing.

Task runs (verify, review, acceptance) use the entry's optional `target` (a
registered run target) as an explicit selection; without it they use automatic
routing and the bot logs `routing.auto`. Session turns always use
provider/model/reasoningEffort.

### 7.3 Concurrency and load back-off

- At most `maxActiveItems` items in `dispatched`..`ready`.
- At most one item per project holds that project's delivery lane
  (`accepting`..`completing`). The lane is shared by all bots of the workspace,
  so items of different projects deliver in parallel while each project
  delivers one item at a time.
- New dispatch is skipped while any of these hold: daemon active executions
  near the execution cap, any execution `queued` longer than a threshold,
  event-loop lag above a threshold. Back-off doubles the poll interval up to a
  maximum and resets when healthy.

### 7.4 Merge, push and release authorization

Per project `merge`, `push` and `release` flags are the user's standing
authorization for the bot. Without `merge`, an accepted item parks with
"ready to merge". Without `push`, merged items stop at local merge and the
notification says "not pushed". `release` (default disabled) allows the bot to
dispatch the project's own release procedure after a configured number of
user-visible deliveries or a delivery marked critical; it is the last stage to
implement and follows each project's instructions. `mode: dryRun` overrides
all of them (§13). Release is the last stage to implement and is disabled by
default; it never upgrades, restarts or reinstalls the app or daemon the bot
runs in.

### 7.5 Quiet hours

During quiet hours the actions listed in `defer` (default `notify`) are held
and sent afterwards, still one message per item. Parked questions are also
deferred unless the item is marked urgent.

## 8. Acceptance

- Run after a successful rebase, against the rebased worktree head, using the
  builtin `test` task bound to the item's worktree with the `acceptance`
  model.
- The plan from `bot-verify` lists required checks with a surface:
  - `daemon`: isolated daemon in a temp dir (`WRENYARD_IPC_PATH`,
    `WRENYARD_CONFIG_HOME`, `WRENYARD_STATE_HOME`), real requests, numbers.
  - `renderer`: source Desktop against that daemon over CDP, driven by the
    managed `browser` operation component (agent-browser CLI); screenshots of
    the real window.
  - `native` (menus, tray, dock, dialogs): the managed `desktop` operation
    component (Cua Driver).
  The builtin `test` task still selects them through its `capability` input
  (`browser-use` → `browser`, `computer-use` → `desktop`); the bot passes no
  execution-feature flags of its own. Project-specific recipes are prose in
  the project instructions or the bot config, never hard-coded.

Component readiness: before starting acceptance the bot calls
`components.action { id, action: 'refresh' }` for each component the plan
requires and then reads `components.list`; a component whose state is not
`ready` (`not-installed`, `installing`, `needs-authorization`, `failed`,
`unsupported`, `disabled`) parks the item with the component name, state and
host and raises one escalation, instead of running acceptance and reporting a
downgrade. The `desktop` component has one owner per host, so desktop
acceptance runs are serialized across all projects; a busy desktop leaves the
item in `accepting` and retries on a later tick.

- Acceptance output: `checks[]` of `{ claim, method, status: verified |
  failed | not_verified, evidence: [artifact paths], note }`. Static checks
  (lint, typecheck, code reading) never count as `verified` for a runtime
  claim.
- Gate: `accepted` only if every required check is `verified`. Any `failed`
  → `rejected` with the failing evidence sent to the session. A required
  `not_verified` (driver missing, surface not capturable) → `parked` with the
  reason, unless the item policy allows delivering with an explicit
  not-verified note.
- Evidence artifacts are kept with the item and attached to the notification.
- Acceptance never touches the user's installed app or real daemon state;
  fault injection happens only inside the worktree and must be reverted before
  merge (the clean-tree check enforces it).

## 9. Supervision

- Tick (default 60 s): advance items whose next action is due, run
  watchdogs. Inbox poll on its own cadence (default 10 min) plus `bot.tick`
  on demand. Judgment runs only on change (new session events) or idle
  timeout, not every tick.
- Watchdogs:
  - session silent while running beyond a threshold, or waiting on the user;
  - a bot item's execution `queued` beyond a threshold, or running with a cwd
    outside its worktree;
  - daemon active work near the cap; event-loop lag;
  - repeated adapter failures;
  - step `unknown` states;
  - a component required by an item's acceptance plan is not `ready`.
- Budgets per item (`maxCorrections`, `maxAcceptanceAttempts`,
  `maxItemHours`) and per bot (`maxItemsPerDay`). Exhausting an item budget
  parks it; repeated failure moves it to `failed`.
- Escalation: one notifier message per new condition, rate-limited, plus a
  Bot page banner. The bot never restarts the daemon; an unhealthy daemon is
  escalated to the user.

### 9.1 Health and endurance

`bot.health { botId }` returns `uptimeSince` (host start), `ticks` (ticks since
start), `lastTickAt`, `tickLagMs` (last and max delay between the scheduled and
actual tick start), `itemsByState`, `stepsFailed24h`, `adapterErrors24h`,
`escalations24h` and `lastError` (`{ at, code, message }`). It also returns
`host { hostname, platform, arch, daemonVersion, mode }` — the device and
daemon the bot runs on, where `mode` is `installed` or `source` — and
`components [{ id, state }]` from the cached `components.list`, refreshed only
before acceptance or by the user. The 24h counters
are computed from `bot_step` and `bot_log`, so they are correct across daemon
restarts. The Bot page shows these numbers. The acceptance criterion for Bot
mode as a whole is at least 8 hours of continuous unattended operation on the
installed app, measured by these numbers: ticks advance without gaps beyond
the cadence, `tickLagMs` stays bounded, and every failure appears in the
counters and the log.

## 10. Desktop Bot page

A new shell page `bot` in the primary navigation, separate from the session
list:

- Header: bot selector, state, `dryRun` badge, pause/resume/stop, run-now,
  last tick, next poll, load status, the device and daemon the bot runs on
  (`bot.health.host`), and whether Desktop is connected to the local daemon or
  a WY Remote host (`远程 · <displayName>`); bots always belong to the daemon
  Desktop is connected to, so switching connection switches the bot list.
- Health: the `bot.health` numbers (`uptimeSince`, `ticks`, `lastTickAt`,
  `tickLagMs`, `itemsByState`, `stepsFailed24h`, `adapterErrors24h`,
  `escalations24h`, `lastError`) and the `components` states.
- Pipeline: one row per item with state, project, class, age, session link
  (opens the session page or Mini), worktree, head/merged sha, acceptance
  checks with evidence thumbnails, last error.
- Decisions: parked questions with answer box/options and dismiss/retry.
- Live log: `bot.log` cursor stream.
- Config: effective config summary (adapter kinds and names, no argv or env
  values), config path, validation result.

Data uses TanStack Query polling through the shell bridge (like schedules).
Work sessions remain ordinary sessions; the session list may show a small bot
badge from session metadata, but bot judgment tasks never appear there.
Product UI text is Chinese per project language rules.

## 11. Security boundaries

- No secrets in the repository, ledgers, bot tables or logs. Config lives in
  the config home; secrets come from environment references at run time.
- Item text is user content stored only in local state.
- `bot.*` methods accept only the local IPC transport; session transports
  cannot control bots.
- Worktrees owned by a bot (`owner` metadata) can be merged only by the bot
  host; `project.worktree.merge` from any other caller is rejected with
  `bot_owned`. Sessions therefore cannot self-merge bot items.
- Merge, push, source completion, annotate/release, notify and release run
  only when the bot's mode and the project policy allow them. Push never
  forces; the bot never tags outside an enabled release policy.

## 12. Protocol additions

- `bot.list`, `bot.create`, `bot.update`, `bot.control` (`start` | `pause` |
  `resume` | `stop`), `bot.delete`, `bot.tick`, `bot.health`,
  `bot.config.validate`.
- `bot.items` (filter by state), `bot.item.get`, `bot.item.action`
  (`retry` | `dismiss` | `answer` | `cleanup`).
- `bot.log` `{ botId, afterSeq, limit?, waitMs? }`.
- `project.worktree.rebase` `{ project, worktree_id }` →
  `{ rebased, head_sha?, conflicts?: [path], target_commits?: [{ sha,
  subject, files }], error? }`; aborts the rebase on conflict.
- Worktree metadata `owner` and the merge guard above.

## 13. Dry run

`mode: dryRun` runs verify, dispatch, sessions, supervision and acceptance for
real, but replaces `merge`, `push`, `inbox.complete`, `annotate`, `release`,
`notify` and release with journal entries of what would have happened,
including the would-be message text. Items move through the same states with
a `dryRun` mark. Switching a bot to `live` does not replay recorded dry-run
effects.

## 14. Delivery plan

Stage 2, MVP-first order, each a separate commit with `Refs: bot-mode`:

(a) Persistence tables, bot host with state machine and step journal, `bot.*`
protocol methods and `bot.health`; small state-machine tests.
(b) Command adapters (inbox, notifier) with validation, timeouts and redacted
logging; source-withdrawal checks.
(c) `project.worktree.rebase`, worktree `owner` and the merge guard.
(d) `bot-verify` and `bot-review` task definitions and acceptance wiring to
`test`.
(e) A minimal Bot page: header with health, pipeline, decisions, log.
(f) Dry-run end-to-end demo in an isolated daemon with fake inbox/notifier
scripts under a temp dir, and the adapter configuration guide with neutral
examples. MCP adapters and UI polish follow later.

## 15. Review decisions (2026-10-16)

1. Judgment runs as per-step structured task runs (bounded, inspectable); no
   hidden ledger session.

3. The delivery lane is per project, shared across bots; one bot can deliver
