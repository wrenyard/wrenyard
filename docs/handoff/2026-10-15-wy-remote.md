This handoff describes what is actually implemented for WY Remote, what was

coordinator must take for real-target and first-install acceptance. It does not
claim complete real-target verification.

## 1. What is implemented

- **SSH discovery and validation** — `apps/desktop/src/main/remote/ssh-discovery.ts`
  enumerates concrete `Host` aliases (including `Include`), resolves the effective
  configuration with `ssh -G`, rejects option/newline injection, and never lists
  wildcard or negated patterns.
- **SSH stdio relay** — `apps/desktop/src/main/remote/ssh-relay.ts` bridges the
  remote daemon's owner-only IPC to a single local owner-only endpoint (Unix
  socket, or Windows named pipe) through the daemon bundle's
  `--stdio-bridge --connect-to <ipcPath>` entry. Frames pass through untouched;
  buffering is bounded in both directions; only owned relay/daemon processes are
  cleaned up. Remote command quoting is platform-specific: POSIX single-quoting
  (embedded single quotes escaped, NUL/CR/LF refused) and Windows `cmd.exe`
  double-quoting that **fails closed** on any value containing `"`, `%`, `!`,
  NUL, CR or LF (no backslash-escaped quote is ever emitted). Node sources travel
  base64-encoded through a fixed loader; PowerShell steps use `-EncodedCommand`.
- **Bootstrap / first install** — `apps/desktop/src/main/remote/bootstrap.ts`
  provisions a versioned per-user payload under `<home>/.wrenyard/remote/<version>`
  from the shared update feed's `remote_payloads` (same `WRENYARD_UPDATE_BASE_URL`
  convention as the Desktop updater). The archive digest is re-verified on the
  target; extraction goes into a unique owned sibling staging directory, then a
  `READY` marker (version + target + sha256) is written inside staging and the
  tree is atomically renamed into the final prefix; an existing `READY` prefix is
  refused, never overwritten. Before publishing the ready payload the staged
  payload is verified with the remote bundled Node: required entries,
  `SUITE_VERSION` equals the exact version, and the **staged runtime's actual
  `process.platform`/`process.arch` equals the selected target**. Reuse of an
  existing prefix applies the same checks (metadata + entries + actual
  platform/arch). A live daemon is probed for the exact product and protocol
  version: a compatible one is adopted, a reachable-but-malformed/erroring/
  version-mismatched endpoint fails closed. Pre-extraction staging uses native
  POSIX/PowerShell tooling only.
- **Payload / feed pipeline** — `tools/release/remote-payload.mjs` builds
  per-target archives (`darwin-arm64`, `win32-x64` only; others refused) from the
  existing staged `resources/wrenyard` closure, with a target-native closure
  assertion for cross-source-and-target builds. `tools/release/pack.mjs` builds
  the target payload during packaging; `tools/release/publish.mjs` requires the
  archives, checksum sidecars and metadata before publishing;
  `tools/release/update-feed.mjs` and `packages/protocol/src/update-feed.ts` add
  the optional `remote_payloads` field (`wrenyard.update.v1`).
- **Single active context** — `apps/desktop/src/main/remote/context.ts` plus
  `apps/desktop/src/main.ts`: generation-fenced states
  `local`/`connecting`/`remote`/`disconnected`. Business access is allowed only
  for a committed endpoint (`local` or `remote`), so `connecting` and
  `disconnected` deny business operations; a switch is refused while user work or
  daemon activity is in flight.
  Only a failure *before* host-registry persistence rolls back to the previous
  local context. Once `start()` has resolved the save has already succeeded, so
  the commit is fail-closed: a failure of the post-start endpoint apply
  (`applyEndpoint`) or of the cache refresh (`resetCaches`/`refreshCaches`) does
  **not** fall back to the previous local context and does **not** report
  `failed-unsaved`. Instead the saved host and the remote endpoint intent are
  retained, the context moves to an explicit `disconnected` state with an
  actionable message, and that state is emitted so the renderer root overlay
  unmounts business pages while `allowsBusinessOperations()` stays `false` until
  the user reconnects or explicitly returns to local. The potentially throwing
  `applyEndpoint`/`emit` during the commit are contained so they cannot be
  misrouted into the pre-save rollback branch, generation fencing is unchanged,
  and a rejecting reset surfaces an error message rather than throwing or looping
  recursively. A tunnel loss after a committed remote stays explicit
  remote-disconnected with no local fallback.
- **Daemon operations** — `remote.host.list` / `remote.host.save` /
  `remote.host.rename` (secret-free registry persisted atomically at mode `0600`;
  `save` requires `ready: true`), plus `workspace.inspect` and
  `workspace.initialize`; the stdio bridge is `daemon --stdio-bridge
  --connect-to <ipcPath>`, which emits one clean NDJSON stdout and refuses any
  network endpoint.
- **Desktop surfaces** — typed preload/shell contract for the remote channels,
  the Daemon menu entry and remote connect dialog/list/rename UI, remote-aware
  media path handling, and context-change resets across session/draft/provider/
  quota/statistics/Pet caches.

## 4. Known functional blockers for real acceptance

1. **No real SSH target.** First connect and first install require a
   coordinator-controlled clean target reachable with strict, already-enrolled
   host trust and non-interactive authentication.
2. **No published matching-version remote payload.** The existing published
   same-version feed has **no new remote payload**, so first-install acceptance
   needs the coordinator to build **both native payloads** and a
   **matching-version feed** for the candidate, then set
   `WRENYARD_UPDATE_BASE_URL` to a controlled source (or use a later approved
   release). **Immutable published version metadata must not be modified.**
3. **Windows path unexecuted** (see §3).

## 5. Coordinator commands (inferred from current scripts)

- Static checks: `pnpm lint`, `pnpm check`.
- Tests (existing suites only): `pnpm test`.
- Build one remote payload from an already-staged closure:
  `node tools/release/remote-payload.mjs --stage <staged-dir> --version <x.y.z> --target <darwin-arm64|win32-x64> [--source <triplet>] [--out <dir>]`.
- Full packaging for the current target (also builds that target's payload):
  `pnpm release <x.y.z>`.
- Generate the matching-version feed document:
  `node tools/release/update-feed.mjs <metadata-dir> <assets-dir> --version <x.y.z> --repository <owner/repo>`.
- Point the Desktop at a controlled feed: set `WRENYARD_UPDATE_BASE_URL`.

Build each payload on its own target runner so the staged native closure is
genuine.

## 6. Coordinator acceptance checklist

1. Both targets install, and a **cross-source-and-target** build is exercised.
2. Strict **existing SSH trust** (no auto host-key acceptance).
3. **First install runs once** on a clean target and remembers one host.
4. A **saved host reconnects directly** with no duplicate install.
5. A failed **auth / key / checksum / version** attempt saves nothing.
6. **Rename persists** across reload.
7. A **sentinel remote** host shows remote business context while the **local
   sentinel** stays untouched.
8. **Attachments** upload explicitly to the remote.
9. **Disconnect** shows explicit remote-disconnected with **no local fallback**.
10. **Explicit return-local** clears remote views.
11. An **active session blocks a switch**.
